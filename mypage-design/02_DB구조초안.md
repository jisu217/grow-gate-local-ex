# DB 구조 초안 (마이페이지 관점)

> 마이페이지 화면을 그리기 위해 어떤 테이블이 왜 필요한지 정리
> 기준: backend/BE-01/erd.md (기존 ERD) + 마이페이지에 필요한 추가 제안
> 작성: 혜원 / 2026-06-21

---

## 1. 한눈에 보는 테이블 ↔ 마이페이지 카드 매핑

| 테이블 | 마이페이지에서 쓰는 곳 | 왜 필요한가 |
| :--- | :--- | :--- |
| `users` | 로그인 사용자 식별, 계정 정보 | 모든 "내 ~" 데이터의 기준점. 누구의 마이페이지인지 |
| `companies` | 회사 정보 카드 | 기업 계정의 소속/업종 표시, 진단 주체 |
| `products` | 제품 지식 현황 카드 | 내가 등록한 제품 목록의 기준 단위 |
| `product_knowledge` | 제품 신뢰도 카드 | 제품별 신뢰도 등급·출처, 진단 입력 데이터 |
| `certifications` | 만료 임박 인증서 알림 | 만료일 기준 경고(D-90), 데이터 완성도 |
| `diagnosis_runs` | 최근 진단 카드, 오늘 할 일 | 진단 점수·상태·로드맵의 원본 |
| `reports` ⭐신규 | 리포트 보관함 카드 | **현재 ERD에 없음 → 신규 제안** |
| `audit_logs` | 제품 수정 이력 | 누가 언제 무엇을 바꿨는지 추적 |
| `memberships` ⭐신규 | 팀원 권한 카드 | **권한 카드용, ERD 보강 필요** |

## 2. 핵심 테이블 요약 (기존 ERD 기반)

> 컬럼 상세는 `backend/BE-01/erd.md` 참조. 여기서는 마이페이지에 필요한 컬럼만 발췌.

### users (사용자 계정)
- `id`, `email`, `name`, `user_type`(personal/company), `company_id`(FK, nullable)
- → 마이페이지 진입 시 로그인 사용자 식별의 기준

### companies (기업 정보)
- `id`, `name`, `business_number`, `industry`
- → **회사 정보 카드**

### products (제품)
- `id`, `owner_user_id`(FK), `name`, `category`, `updated_at`
- → **제품 지식 현황 카드**의 제품 개수/최근 수정일

### product_knowledge (제품별 수출 지식)
- `id`, `product_id`(FK, 1:1), `trust_grade`(high/medium/low), `source_type`, `notes`
- → **신뢰도 등급 분포** 집계

### certifications (인증서)
- `id`, `product_id`(FK), `name`, `expires_at`, `renewal_cycle`
- → `expires_at` 기준 90일 이내면 **만료 임박**으로 카운트 (서버가 `daysUntilExpiry` 계산해 내려줌)

### diagnosis_runs (AI 진단 실행 기록)
- `id`, `user_id`(FK), `company_id`(FK, null), `product_id`(FK, null)
- `input_data`(JSON), `knowledge_snapshot`(JSON), `result`(JSON), `status`, `target_country`, `created_at`
- → **최근 진단 카드**(최신 1건), **오늘 할 일 카드**(`result.roadmap`)

### audit_logs (수정 이력)
- `id`, `product_id`(FK), `changed_by`(FK), `change_type`, `changed_fields`(JSON), `changed_at`
- → 제품 상세의 변경 이력 탭

## 3. ⭐ 신규/보강 제안 (마이페이지 때문에 필요해진 것)

### 3-1. `reports` 테이블 — 신규 제안 ★중요
과제는 "리포트 보관함"과 `GET /api/report/{run_id}`를 요구하지만,
**현재 ERD에는 reports 테이블이 없다.** 진단 결과(`diagnosis_runs.result`)만으로는
"발행된 리포트 문서"를 따로 보관·재열람하기 어렵다. 아래 테이블을 제안한다.

| 컬럼명 | 타입 | 제약조건 | 설명 |
| :--- | :--- | :--- | :--- |
| id | UUID | PK | 리포트 고유 ID |
| diagnosis_run_id | UUID | FK → diagnosis_runs.id, NOT NULL | 원본 진단 |
| user_id | UUID | FK → users.id, NOT NULL | 소유자(보관함 조회 기준) |
| title | VARCHAR(200) | NOT NULL | 리포트 제목 (제품명+국가 등) |
| file_url | TEXT | - | 생성된 리포트 파일 경로(PDF 등) |
| summary | TEXT | - | 요약(목록 미리보기용) |
| created_at | TIMESTAMP | NOT NULL | 발행일 |

> 관계: `diagnosis_runs` 1 : N `reports` (한 진단으로 여러 버전 리포트 가능)

### 3-2. `memberships` 테이블 — 보강 필요
팀원 권한 카드(owner/admin/editor/viewer)를 그리려면 사용자-회사 간 역할 정보가 필요하다.
백엔드 코드에는 membership 엔티티가 있으나 ERD 문서에는 미반영 → 문서화 제안.

| 컬럼명 | 타입 | 제약조건 | 설명 |
| :--- | :--- | :--- | :--- |
| id | UUID | PK | 멤버십 ID |
| user_id | UUID | FK → users.id | 구성원 |
| company_id | UUID | FK → companies.id | 소속 회사 |
| role | ENUM('owner','admin','editor','viewer') | NOT NULL | 권한 역할 |

## 4. 관계도 요약 (마이페이지 중심)

```
users ──1:N── products ──1:1── product_knowledge ──1:N── knowledge_sources
  │              │
  │              ├──1:N── certifications   (만료 임박 카드)
  │              ├──1:N── fto
  │              ├──1:N── buyer_requirements
  │              └──1:N── audit_logs       (수정 이력)
  │
  ├──1:N── diagnosis_runs ──1:N── reports ⭐신규   (최근 진단 / 리포트 보관함)
  │
  └──N:1── companies ──1:N── memberships ⭐보강     (회사 정보 / 팀원 권한)
```
